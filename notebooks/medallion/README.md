# Medallion Architecture — Retail & E-commerce (Hive + Parquet)

A working, end-to-end medallion implementation on the Yeedu demo tenant. Three
notebooks run in order and build 24 → 20 → 11 Hive tables from ~10 GB of
generated retail source data; a fourth verifies the result.

| # | Notebook | Layer | Produces |
|---|---|---|---|
| 0 | `00_bronze_generate_and_land` | source ➜ **bronze** | 24 raw tables, as-landed, with audit columns |
| 1 | `01_silver_conform_and_cleanse` | bronze ➜ **silver** | 15 conformed dimensions, 3 facts, 2 quality tables |
| 2 | `02_gold_business_marts` | silver ➜ **gold** | 11 business marts |
| 3 | `03_verify_medallion` | read-only | Inventory, DQ ledger, lineage, business answers |

**Data generation is step 0 and only step 0.** `00_bronze_generate_and_land`
creates the entire source estate from scratch — it runs DuckDB's TPC-DS
`dsdgen` on the driver, writes 24 Parquet extracts to
`/scratch/disk1/medallion/landing`, then lands them into `bronze_retail`. Steps
1-3 never generate anything; they only read what step 0 produced. Note that step
0 mints a **new `BATCH_ID`** each time it runs, and silver and gold key their
skip-if-already-built logic off that id — so re-running step 0 means re-running
1, 1b and 2 as well.

## Data

TPC-DS at scale factor 10, generated in-cluster by DuckDB's `dsdgen` — a retail
estate with three selling channels (stores, printed catalogue, web), a product
catalogue, customers with demographics, promotions, returns and warehouse
inventory. **191.5M rows across 24 tables, ~2.8 GB as compressed Parquet
(~10 GB raw).** No external download, no S3 credentials: everything lands in the
cluster's Hive warehouse.

## What each layer actually does

**Bronze — land it raw.** Six simulated source systems (`pos_dw`, `catalog_erp`,
`web_storefront`, `crm_mdm`, `merch_erp`, `ref_data`) drop 24 extracts. Every
row is kept exactly as received and stamped with `_source_system`,
`_source_file`, `_batch_id` and `_ingest_ts`. The notebook deliberately injects
the defects a real feed carries — CDC replays (duplicate rows), unsettled
amounts (null `net_paid`), correction entries (negative quantities), CRM casing
and whitespace noise, three spellings of "United States", missing zips — and
then prints them, so silver has genuine work to do.

**Silver — the trusted model.** Typing (explicit decimals/dates), dedup on
natural keys, standardisation, enrichment, and the conforming step that matters
most: **store + catalog + web sales collapse into one `fct_sales` at a single
grain**, and the three return feeds into one `fct_returns`. Rows that fail the
data contract are *quarantined* in `dq_rejects_sales` with a reason, not dropped
silently. Every rule writes a row into `silver_retail.dq_metrics`.

**Gold — questions, answered.** Eleven wide, pre-aggregated marts named after
the question they answer: daily executive KPIs, channel growth, store league
table, product P&L, category trends, customer RFM segmentation, omnichannel
mix, promotion ROI, returns by reason, inventory health, and category basket
affinity. No joins required downstream.

## Running them

The cluster allows **one job at a time**, so run them strictly in order:

```bash
yeedu notebook start --workspace_id 342 --notebook_id <id> --follow
```

Two things to know about running them:

* **`--follow` is the only way to see cell output** — notebook outputs are not
  persisted on export, and the driver log carries Spark's logger output but not
  the cells' `print()`. But `--follow` also *ties the run's lifetime to the CLI
  process*: kill the client and the run is stopped server-side. So long runs go
  with `--is_background true` and are polled via `notebook get-run`, and
  `03_verify_medallion` exists to print the results afterwards in a run short
  enough to follow safely.
* **A failed `--follow` does not mean no run started.** A 503 on the stream, or
  `RFA-000155: limited to 1 simultaneous job(s)`, still leaves a run created and
  executing. Check `notebook list-runs --run_status running` before relaunching.
* **Runs are reaped after roughly 15-25 minutes.** The Jupyter server takes a
  `signal 15` and the run ends `STOPPED` — no OOM, no traceback, nothing in
  stdout but `Attempting to gracefully kill PID`. Two runs died this way at
  22m11s and 16m05s, so treat the budget as variable, not a fixed wall.

  Every step is therefore written to be **resumable**: `SKIP_EXISTING = True` at
  the top of the silver and gold notebooks makes `publish()` skip any table that
  is already present and carries the current batch id, and intermediate results
  are staged as real tables (`_stg_*`) rather than cached. Relaunching a reaped
  notebook picks up where it stopped instead of starting over, so a long layer
  can be walked forward across two or three runs with no edits.

## Editing

Sources live in `src/*.py` with two cell markers:

| marker | becomes |
|---|---|
| `# %%` | a code cell, the lines after it verbatim |
| `# %% [markdown]` | a prose cell — following `# `-prefixed lines become markdown |

Rebuild the `.ipynb` files with:

```bash
python3 notebooks/medallion/build.py nb              # native markdown  <- ship this
python3 notebooks/medallion/build.py --runnable nb-runnable   # CLI verification only
```

Two flavours, because Yeedu's two runners disagree about prose cells — see
[Prose cells: two builds](#prose-cells-two-builds) below. Every **code** cell is
byte-identical between them, so a CLI run of the `--runnable` build genuinely
proves the notebook you ship.

Then push each notebook with:

```bash
yeedu workspace create-workspace-file --workspace_id 342 \
  --local_file_path <dir>/<name>.ipynb --root_output_dir /notebooks --overwrite true
```

Two traps here, both of which cost a wasted cluster run while building this:

* `--root_output_dir` must be an **absolute** workspace path (`/notebooks`, not
  `notebooks`), and **without it the upload silently lands at the workspace root
  as a brand-new file** — the notebook keeps executing its old content with no
  error anywhere. Always verify a push landed: the response echoes the
  `workspace_file_id` and `file_size_bytes` it actually wrote, so check the id
  matches the `notebook_file_id` from `notebook get` and the size matches the
  local file byte for byte. (`notebook export` is not a good check here — it
  writes a `.zip` somewhere of its own choosing rather than to stdout.)
* `yeedu notebook create --notebook_path` **blanks** an existing file, so create
  first and push content afterwards.

### Prose cells: two builds

The Yeedu **notebook UI** authors and renders real markdown cells, and that is
what an audience should see: proper headings, tables and images, collapsible,
with no Python wrapper around them. `build.py` emits exactly that by default,
in Yeedu's own on-disk cell shape (`cell_uuid`, string `source`,
`metadata.order`), so the notebooks round-trip through the UI unchanged.

**But `yeedu notebook start` feeds every cell to the Python kernel regardless of
`cell_type`.** A native markdown cell kills a headless CLI run on its first line
of prose:

```
[Cell 2/3] ─────────────────────────────────────────
[ERROR] SyntaxError: invalid syntax (712834116.py, line 3)
    | a | b |
Cells: 1/3 completed
```

That was verified twice on platform 2.10.1, so it is the runner and not a
malformed file: once with a canonical nbformat markdown cell (no
`execution_count`/`outputs`, cell `id` present) and once in Yeedu's own exported
UI shape, copied field for field from a notebook the UI wrote. Both failed
identically.

Hence `--runnable`, which wraps the same prose in
`display(Markdown(r"""..."""))` code cells. Use it whenever you want to prove the
pipeline end-to-end from the CLI; push the default build for the demo itself.
In `--follow` output a `--runnable` prose cell prints
`<IPython.core.display.Markdown object>` — that is only the CLI's plain-text
rendering of a rich output.

### Diagrams

The architecture and star-schema diagrams are Mermaid graphs in
`assets/*.mmd`. `assets/render.py` renders them through
[mermaid.ink](https://mermaid.ink), quantises the PNGs to the smallest palette
that still looks right, and `build.py` inlines them as base64 `data:` URIs
wherever a source writes `{{IMG:name}}`. The notebooks therefore carry their own
diagrams: nothing to fetch at view time, nothing to 404 later, and the demo works
air-gapped. Re-render after editing a `.mmd`:

```bash
python3 notebooks/medallion/assets/render.py
```

### Live console output

Every notebook prints through a small set of helpers defined in its first cell
(`banner`, `section`, `working`, `ok`, `skipped`, `metric`, `finished`). Two
things about them matter for a demo:

* **Everything flushes.** `print` is rebound to `functools.partial(print,
  flush=True)`. Without that, a notebook's stdout can arrive in one burst at the
  very end, which reads as "nothing is happening" to an audience.
* **Each step announces itself before the work starts.** `working("building
  fct_sales …")` prints, *then* Spark runs, *then* `ok()` reports rows, seconds
  and throughput. The pause is narrated rather than silent.

```
▸ 1.6  THE CONFORMING STEP — ONE FACT FROM THREE CHANNELS
──────────────────────────────────────────────────────────────
   … staging _stg_sales to disk …
   ✓ fct_sales                     2,399,460 rows   14.2s   168,976 rows/s
   ~ dim_customer                    500,000 rows       —   already written for this batch
```

## Scale, and why silver processes a slice

`SCALE_FACTOR` in notebook 0 controls how much data is *generated*. It is SF=10,
so bronze lands the full **192,347,550 rows across 24 tables** — a raw layer
should look like a real raw layer. Generation 2.3 min, landing 3.5 min.

`KEEP_PCT` in notebooks 1 and 1b controls how much of that silver *processes*,
and it is set to **5**. Dimensions are always built whole, and `fct_inventory`
is not sliced at all (6.65M rows); only the three sales/returns facts are cut.
Every join, every mart and every business question is still answered against
complete reference data.

The slice is taken on `hash(natural key) % 100 < KEEP_PCT`, not with `.sample()`.
That is deliberate: random row sampling would separate a CDC replay from the row
it duplicates, quietly destroying the duplicate-detection and quarantine story
that this layer exists to demonstrate. Hashing the key keeps every replay of a
kept order together. Set `KEEP_PCT = 100` on a cluster with room for it.

**After changing `KEEP_PCT`, set `SKIP_EXISTING = False` for one run.** The
staged tables from the previous scale would otherwise be skipped and silently
reused at the wrong volume.

## What this cluster can and cannot do

`onprem-l` is 8 cores sharing a **2.85 GB** driver heap in `local[*]` — the
driver *is* the executor — and `has_local_disk: False`, so every spilled byte
goes to a network-attached volume.

**`spark.sql.shuffle.partitions` is the setting that matters here, and the
default of 200 is wrong for this cluster.** Five consecutive silver runs were
reaped at 15-25 minutes having produced nothing, and the cause was not data
volume, heap pressure or spill — it was 200 shuffle partitions on 8 cores,
across roughly 25 table writes. A measured probe made it obvious: writing
292,265 rows took **20.1 seconds**, almost all of it task scheduling, while
counting 29M rows took 1.2s. Setting it to **16** took silver from
"never finishes" to **136 seconds**. If a step on this cluster goes from slow to
never-completing, check the partition count against the core count before
assuming spill.

Measured end to end at the current settings:

| notebook | duration |
|---|---|
| 0 — bronze generate and land | ~7 min |
| 1 — silver conform and cleanse | 136.5s |
| 1b — silver returns and inventory | 79.3s |
| 2 — gold business marts | 112.9s |
| 3 — verify | 41.5s |

Runs are still reaped after roughly 15-25 minutes with `signal 15` and no
traceback — stdout just ends with `Attempting to gracefully kill PID`. Nothing
here comes close to that ceiling any more, but the `SKIP_EXISTING` resume design
is kept so a reap costs one step rather than the whole pipeline.

Per-notebook `--driver-memory` is rejected on a `YEEDU` cluster type
(`Cannot provide the following Notebook configurations ... for cluster type
'YEEDU'`), and raising it cluster-wide means editing
`max_parallel_spark_job_execution_per_instance`, which requires stopping the
cluster. So the heap is a fixed constraint, not a dial — which turned out not to
matter.

## Two things to know when debugging a run

* **Cell `print()` output does not appear in `notebook logs`.** It goes to the
  Jupyter iopub channel, so a background run is effectively silent — only
  `--follow` shows it. Five of the runs above were debugged from indirect
  evidence for want of this. Always `--follow`.
* **`.show(False)` is a bug, not a truncate flag.** `show()`'s first positional
  argument is `n`, so this raises `PySparkTypeError: Argument 'n' should be an
  int, got bool`. Use `.show(truncate=False)`.
* **`RFA-000155` still creates a run.** The cluster takes one job at a time, and
  launching while the previous run is releasing fails with
  `limited to 1 simultaneous job(s)` and `Run ID: None` — but a run *is* created,
  with nothing attached to drive its cells. It then sits `RUNNING` until the
  reap, blocking everything behind it. After any failed launch, check
  `notebook list-runs --run_status running` and `notebook stop` the orphan.
  Leave a gap between sequential notebook runs.
